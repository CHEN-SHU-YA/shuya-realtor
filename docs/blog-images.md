# 部落格圖片怎麼放

> 📍 **這份說明放在 `docs/`，不要搬回 `public/`。**
> `public/` 底下的每一個檔案都會被原樣公開（這份說明原本放在 `public/blog/README.md`，
> 實測直接連得上、回 200，已經移出來了），內部施工說明對外開放沒有好處。
> 也不要改用 `robots.txt` 擋——那等於在公開檔案裡昭告有這份文件。

圖片的實體位置是 `public/blog/`。網站上的路徑 `/blog/…` 就等於那個資料夾底下的檔案路徑，**不用另外設定**。

> 🔴 那裡的每一張圖都會被公開，也會被 Google 抓走。
> 上傳前逐張確認：**沒有客戶姓名、門牌號碼、車牌、可辨識的人臉、真實成交價格**。
> 屏東是小地方，一張照片就可能被對號入座。

## 一、資料夾長什麼樣

```
public/blog/
├── .gitkeep
├── og-blog.png                        ← 列表頁／分類頁共用的分享圖
├── 1001-pingtung-townhouse-site-visit/   ← 一篇文章一個資料夾
│   ├── cover.png                      ← 封面（每篇必備）
│   ├── fig-01.png                     ← 內文插圖，從 01 開始
│   ├── fig-02.png
│   ├── fig-03.png
│   ├── fig-04.png
│   └── fig-05.png
└── 1002-chongda-xincheng-military-village/
    └── cover.png
```

🔴 **這底下的 PNG 全部是機器產的，不要用小畫家或 Figma 直接改。**
改圖請改 `scripts/build-blog-images.mjs` 再重跑（見下一節）——
手改的那一版會在下一次有人重跑腳本時被無聲蓋掉。

**資料夾名稱 ＝ 文章編號 + 連字號 + slug**，也就是文章網址的最後一段。

| 文章 | 網址 | 圖片資料夾 |
|---|---|---|
| 編號 1001、slug `pingtung-townhouse-site-visit` | `/blog/1001-pingtung-townhouse-site-visit` | `public/blog/1001-pingtung-townhouse-site-visit/` |

🔴 **資料夾名稱打錯，圖片不會壞得很明顯**——版面照排，只是圖變成破圖。
新增文章時，直接把 `.tsx` 檔名（去掉 `.tsx`）複製過來當資料夾名，最不會錯。

## 二、圖是怎麼生的（產圖腳本）

**腳本：`scripts/build-blog-images.mjs`　跑法：`node scripts/build-blog-images.mjs`**
（要在專案根目錄跑，不然 node 找不到 `sharp`。這支不在 `npm run build` 流程裡，
圖是產物、要 commit 進版控，不是每次建置重產。）

作法是 **寫 SVG → 用 `sharp` 轉 PNG**。`sharp` 內建的 libvips 帶了 pango／fontconfig，
吃得下 SVG 裡的中文，所以整張圖的文字、色塊、線條都是程式排出來的，
沒有任何一張是外面畫好丟進來的點陣圖。

**為什麼要這樣做**：圖上有經紀業名稱、分類名、社區戶數這些會變的字。
手繪圖改一個字要重畫；腳本改一行字重跑就好，而且每張圖的色票、字型、留白天生一致。

### 美術方向（不要自作聰明）

- **不畫人物、不畫房子照片、不模仿手繪漫畫。** 走排版型／示意圖型：
  大字標題 ＋ 幾何色塊 ＋ 極簡線條。畫不出同等品質的東西，硬做只會廉價。
- **色票只准用 `blog.css` 的 `--bl-*` 代幣**（腳本裡的 `PALETTE`）。不要臨時調色。
- 圖上**不出現價格、行情、實價登錄**，任何數字都要是事實庫已查證的，
  而且要在該張圖的函式上方註明出處（`cover1002()` 是現成範例）。

### 🔴 封面只放「來源不打架」的數字

「事實庫查得到」還不夠，**封面要求更高一階：多份來源要對得起來**。

理由是封面塞不下但書。內文可以寫「A 資料寫 93 年、B 資料寫 89 年，請以建物登記謄本為準」，
封面只有一行字的空間，寫上去就變成把有爭議的一方當定論——而封面正是 `og:image`，
是分享到 LINE／FB 第一眼看到、也是唯一會被看到的那一句。

實例（2026-08-15 修掉的）：1002 封面原本寫「2004 年完工」。
崇大新城的完工年份有兩份**公部門**資料在打架，差了四年
（國家文化記憶庫民國 93 年 9 月／榮民文化網民國 89 年 9 月 7 日）。
文章第四節整整一節在講這件事，封面卻寫死其中一個版本。
**處理方式是把年份拿掉、換成兩邊都對得起來的「22 棟、14 層樓」**，
不是在封面補一行小字——補了也沒人看，還把版面塞爆。

判斷順序：
1. 這個數字事實庫查得到嗎？查不到 → 不要放。
2. 有沒有第二份來源寫不一樣？有 → **不要放在封面**，留給內文並列。
3. 內文已經處理過的爭議，封面也不能偷偷寫死其中一邊——**兩邊要一致**。

### 🔴 中文字型（這一段是踩過才知道的）

字型是從**作業系統**找的，不是從專案找的。本機（Windows）實測：
`Noto Sans TC` 沒裝 → fallback 到 `Microsoft JhengHei`，中文、粗體、全形空格都正常。
所以 SVG 的 `<style>` 一定要寫完整 fallback 鏈
（`"Noto Sans TC","PingFang TC","Microsoft JhengHei",sans-serif`）。

**換機器（尤其 Linux CI）重跑之前，先開一張圖看中文有沒有變成豆腐方塊。**
不要只看到「檔案產出來了」就當作成功——字型掉了照樣產得出 PNG，只是字全是方塊。
真的掉了就在那台機器裝一套 Noto Sans TC。

### 腳本會自己驗什麼、不會驗什麼

跑完會逐張讀回來檢查 **格式是 PNG、尺寸正確、檔案 ≤ 500 KB**，任一項不過就 exit 1。
另外會用估算的字寬檢查「文字有沒有超出框線」，超出只印警告不擋（估算不是量測）。

❌ **驗不到的**：中文有沒有渲染成方塊、有沒有錯字、線條有沒有壓到文字、
語意對不對（例如圖例寫「兩者的落差」但色塊其實塗滿整塊地）、
**圖上的事實是不是有爭議**（上一節那條，1002 封面就是這樣寫死了一個有兩份公部門
資料在打架的年份，尺寸與大小全都 OK 照樣過關）。
**這五項只能自己開圖看**，腳本印的最後一行就是在提醒這件事。

### 怎麼加新圖

1. 在腳本裡寫一個回傳 SVG 字串的函式（照現有的 `fig01()`、`cover1002()` 抄）。
2. 加進檔案最下面的 `IMAGES` 陣列：`{ file, w, h, svg }`。
   `file` 是相對 `public/blog/` 的路徑，資料夾不存在腳本會自己建。
3. 跑 `node scripts/build-blog-images.mjs`。
4. **把圖打開看**（上一段那四項）。
5. 插圖的話，順手確認文章 `.tsx` 裡的 `alt` 描述的是**圖上真正有的東西**。
   改了畫面就要一起改 `alt`——`alt` 是寫給看不到圖的人的，描述錯了比沒寫更糟。

🔴 **不要用亂數、不要讀當下時間。** 同樣的原始碼要能產出位元組相同的 PNG，
不然每次重跑 git 都會看到一堆假異動（現況已實測：連跑兩次 MD5 完全相同）。

## 三、檔名與尺寸

| 用途 | 檔名 | 尺寸 | 格式 | 備註 |
|---|---|---|---|---|
| 文章封面 | `cover.png` | **1200 × 630** | PNG | 每篇一定要有。同時是 `og:image` 與 JSON-LD 的 `image` |
| 內文插圖 | `fig-01.png`、`fig-02.png`… | **1200 × 675**（16:9） | PNG | 兩位數補零，從 `01` 連號，中間不跳號 |
| 列表頁分享圖 | `og-blog.png`（放最外層） | **1200 × 630** | PNG | 全站共用一張，`/blog` 與五個分類頁都用它 |

規則：

1. **副檔名一律小寫 `.png`。** 不要 `.PNG`、不要 `.jpg`、不要 `.webp`。
2. **檔名全小寫、只用英數與連字號。** 不要中文檔名、不要空格、不要底線。
3. **1200 × 630 是社群分享的規格，不能改。** Facebook 與 LINE 的預覽圖就是照這個比例裁的，
   換成正方形或直式，分享出去會被切掉標題。
4. **插圖用 1200 × 675。** 文章正文的容器是 720px 寬，1200px 是為了在高解析度螢幕上不糊；
   高度固定成 675 是為了讓每篇文章的圖高度一致，滑動時不會忽高忽低。
5. **單檔建議 300 KB 以內、上限 500 KB。** 超過的先壓縮再放進來——
   插圖是 `loading="lazy"`，但封面是 `eager`，封面太大會直接拖慢手機第一屏。

### 程式會幫你擋什麼、不會擋什麼

`src/lib/blog.ts` 的 `auditPosts()` 在 `npm run build` 時會**直接 throw**（建置紅掉、產不出東西）：

- ✅ **非草稿文章的封面圖不存在** → 擋。缺封面會同時弄壞三處：首屏 `eager` 大圖（正好是 LCP）、
  `og:image`（分享出去一片白）、JSON-LD 的 `image`（結構化資料無效），而且三處都不會報錯。
- ✅ **列表頁／分類頁的 OG 圖不存在** → 擋。
- ✅ **非草稿文章的正文沒有揭露經紀業名稱** → 擋。
- ❌ **插圖（`fig-XX.png`）打錯或漏放** → **不擋**，插圖路徑寫在文章 JSX 裡，程式看不到清單。
  這一項只能靠發文前自己把文章滑到底看一次。
- ❌ **圖片尺寸不對、檔案太大** → 不擋。

草稿（`draft: true`）一律略過上面三項檢查——寫到一半沒圖是正常狀態。
**但 `draft` 一拿掉，圖就必須到位，否則建置直接失敗。**

## 四、程式端怎麼引用（寫文章的人要知道）

**封面不用自己寫路徑。** 文章頁會自己組出 `/blog/{編號}-{slug}/cover.png`，
`alt` 也會自動帶入文章標題全文，`.tsx` 檔裡什麼都不用填。
只有極少數要換封面檔名的情況，才在文章資料裡加 `cover: "另一個檔名.png"`。

**插圖要自己寫**，寫在文章 `.tsx` 的 `body` 裡，格式固定：

```tsx
<p>
  <img
    src={`${MEDIA}/fig-01.png`}
    alt="說明圖：畫面裡有什麼、誰在做什麼（30–55 字的具體描述）"
    width={1200}
    height={675}
    loading="lazy"
  />
</p>
```

四個不能省的細節：

- **包在 `<p>` 裡、不要加 class**，樣式靠 `.bl-prose img` 吃。
- **`width` / `height` 一定要寫**，不寫會有版面跳動（CLS），Google 會扣分。
- **`loading="lazy"`**（封面是 `eager`，封面由程式產生，不用你管）。
- **`MEDIA` 是文章檔頂端自己定義的常數**，值是 `/blog/{編號}-{slug}`。
  文章檔不能 import `@/lib/blog`（會循環相依，後果是文章全部無聲消失），
  所以這一行是手寫的，改編號或 slug 時要一起改。
  ⚠️ **法遵字串不在此限**：經紀業名稱、職稱、署名列請
  `import { AGENCY, ARTICLE_SIGNATURE } from "@/lib/agency"`——
  那一支只 import `profile.ts`，不會成環，**不要自己重打字串**。

## 五、`alt` 怎麼寫（這一段比尺寸重要）

`alt` 是寫給看不到圖的人與搜尋引擎看的，**寫的是畫面，不是關鍵字**。

- ✅ `說明圖：一條看起來很平常的巷子，路面上浮出幾塊半透明的地號方框，其中一塊方框裡站著一個手拿權狀的陌生人`
- ✅ `說明圖：同一棟透天的兩個畫面並排，左邊晴天地面全乾，右邊下雨天門口積水成一灘、牆角浮出一條深色水痕線`
- ❌ `屏東透天 買房 注意事項 屏東房地產 書亞`（關鍵字堆疊，沒有描述畫面）
- ❌ `圖片1`（等於沒寫）

長度抓 **30–55 字**，句型兩種擇一：
`說明圖：{畫面元素與關係}` 或 `Q 版四格漫畫：{分鏡1}、{分鏡2}、{分鏡3}、{分鏡4}`。

封面的 `alt` 由程式自動帶入文章標題全文，不用也不能自己填。

## 六、插圖要放幾張、放在哪一節

| 版本 | 封面 | 插圖 |
|---|---|---|
| 精簡版（8–10 節） | 1 張 | 4–5 張 |
| 旗艦版（13–14 節） | 1 張 | 6–7 張 |

放圖的規律只有一條：**只放在抽象、需要畫面感的節**——
「兩件事會分家」「時間過去了才爆」「數字有落差」這種文字講不清楚的概念。

程序性的節（文件清單、地雷總表、行動清單、FAQ）**一張圖都不放**。
節奏上大約每 1–3 個章節一張，多半擺在該節的收尾處。

## 七、新增一篇文章的圖片，動作清單

1. 在 `scripts/build-blog-images.mjs` 寫封面的函式，加進 `IMAGES`，
   `file` 填 `{編號}-{slug}/cover.png`（1200 × 630）——**資料夾名稱直接抄文章的 `.tsx` 檔名**。
2. 插圖同樣加進 `IMAGES`，命名 `fig-01.png`、`fig-02.png`…（1200 × 675），中間不要跳號。
3. 跑 `node scripts/build-blog-images.mjs`。尺寸與 500 KB 上限它自己會擋。
4. **逐張開圖看**：中文有沒有變方塊、有沒有錯字、線條有沒有壓到文字、圖例跟畫面對不對得起來。
5. 再看一次：**有沒有出現姓名、門牌、車牌、人臉、真實價格**，以及未查證的數字。
6. 對照文章 `.tsx` 的 `alt`，確認描述的是圖上真正有的東西。
7. 本機跑起來，把文章頁滑到底，確認沒有破圖、沒有版面跳動。
8. 要正式發布（拿掉 `draft`）之前跑一次 `npm run build`——封面沒放好會直接紅。

## 八、常見問題

**Q：圖片路徑 `/blog/1001-xxx/cover.png` 跟文章網址 `/blog/1001-xxx` 長得一樣，不會打架嗎？**
不會。Next.js 會先找 `public/` 底下的實體檔案，找不到才走路由，
所以 `/blog/1001-xxx/cover.png`（有副檔名）走靜態檔、`/blog/1001-xxx`（沒有）走文章頁。
萬一以後真的出問題，把整個 `public/blog` 改名，然後只改 `src/lib/blog.ts` 裡 `MEDIA_BASE` 那一行。

**Q：可以用 `next/image` 嗎？**
不行。部落格的版型是照著既有設計 1:1 復刻的，`next/image` 會自己包一層容器、加自己的 class 與 srcset，
CSS 會對不上；而且它要改 `next.config.ts`，那個檔案不能動。一律用原生 `<img>`。

**Q：文章還沒發布（`draft: true`），圖片要先放嗎？**
可以先放。草稿在本機（`next dev`）看得到，列表頁上會標「草稿」，正式站則完全找不到。
`draft: true` 的文章不進 sitemap，所以圖片也不會被 Google 主動抓走。

**Q：`og-blog.png` 畫好了，還要做什麼？**
✅ **已經做完了（2026-08-15）**，這一題留著只是給日後換圖的人看流程。
`src/lib/blog.ts` 的 `BLOG_META.ogImage` 已改成 `/blog/og-blog.png`，
`BLOG_OG_IMAGE` 的 `width` / `height` 也一起改成 1200 / 630
（實體檔以 sharp 讀 metadata 確認為 1200×630，建置產物的
`og:image` / `og:image:width` / `og:image:height` 已核對正確）。
之前是暫時指向首頁那張形象照 `/img/shuya-profile.jpg`（1044×1568 直式，社群預覽會被裁上下）。

🔴 **日後換圖時，這兩個地方要一起改**，只改一邊會變成尺寸標錯的 OG 標籤——
路徑改錯 build 會被 `auditSharedAssets()` 擋下來，但**尺寸寫錯沒有任何機制會擋**。

**Q：`scripts/` 底下那兩個 `_fonttest.*` 是什麼？**
產圖前用來確認這台機器的中文字型跑不跑得動的臨時檔，**可以直接刪掉**。

🔴 **請書亞手動刪掉這兩個檔**（連三輪都被權限系統擋下刪除動作，改不掉的只有刪除這個動作）：

```
scripts/_fonttest.mjs
scripts/_fonttest.png
```

2026-08-15 已把兩個檔**清空**：`.png` truncate 成 0 byte，
`.mjs` 只剩一段「這個檔可以刪」的註解、跑起來不做任何事、也不會再產出 `_fonttest.png`。
刪掉不影響 `npm run check`、`npm run build`，也不影響產圖。
